# RAV4 窄巷停車模擬器

[![verify](https://github.com/fuhsinglai/ParkingSimulation/actions/workflows/verify.yml/badge.svg)](https://github.com/fuhsinglai/ParkingSimulation/actions/workflows/verify.yml)

依現場配置重建的窄巷平行停車模擬器。與參考版（`Reference/GPT/`）最大的差別是：

> **路徑不是畫出來的，是搜出來的。停不進去就照實說，並回答「那要改什麼才停得進去」。**

參考版的「示範停入」與「窄巷折車法」是人工挑好的關鍵點做線性內插 —— 車子會橫向
滑移、不做碰撞檢查，把巷寬從 5.9m 拉到 4.8m，動畫還是播一模一樣的路線，
可能直接穿過對面白車。

這一版每一段路徑都由同一個自行車模型積分產生，每一小步都做碰撞檢查。

## 系統啟動

**環境需求**

| 用途 | 需要 | 說明 |
|---|---|---|
| 跑模擬器 | Python 3.7+ | 只用標準函式庫，不必 `pip install` |
| 跑驗證 | Node.js 16+ | 只有 `test/verify.mjs` 需要 |

**啟動步驟**

1. 開終端機，切到專案根目錄（`index.html` 所在的那層）：

   ```bash
   cd "D:/Projects/Parking Simulation"
   ```

2. 啟動開發用伺服器：

   ```bash
   python serve.py
   ```

   看到 `serving on http://localhost:8126` 就算起來了。

3. 瀏覽器開 <http://localhost:8126>。

4. 要關掉時，在終端機按 `Ctrl+C`。

**固定用 `http://localhost:8126` 這個網址。** `localStorage` 是綁「協定＋主機＋
埠號」的，換埠號或改用 `127.0.0.1` 都等於換一個儲存空間，之前存的設定就讀不到了。

需要 HTTP 伺服器是因為用了 ES modules 與 Web Worker，直接雙擊 `index.html`
（`file://`）開不起來。`serve.py` 會送 `no-store`，改了程式重新整理就生效，
不用重開伺服器。

**換埠號**（8126 被占用時才需要，代價是舊設定讀不到）：

```bash
python serve.py 8127
```

也可以用環境變數 `PORT`。編輯器整合的話，`.claude/launch.json` 裡已經有
`parking-sim` 這個設定，走的是同一支 `serve.py` 與同一個埠號。

**驗證規劃器**（不需要先啟動伺服器）：

```bash
node test/verify.mjs
```

會對每個情境重新積分、逐格檢查有沒有碰撞。有情境失敗時腳本會以非零狀態結束。

每次 push 到 `main` 或開 PR，GitHub Actions 都會自動跑同一支腳本，結果看 repo 的
Actions 頁籤，標題上的 badge 也會跟著變。

**啟動不了的時候**

| 症狀 | 原因與處理 |
|---|---|
| `Address already in use` | 8126 已經有東西在跑。先確認是不是自己開過的舊視窗，或改用別的埠號。 |
| 畫面空白、Console 出現 CORS／module 錯誤 | 十之八九是用 `file://` 直接開檔案。回到步驟 2 走伺服器。 |
| 之前存的場景不見了 | 檢查網址是不是 `localhost:8126`。換過主機名或埠號就是另一個儲存空間。 |
| 改了程式沒生效 | 硬重新整理（`Ctrl+Shift+R`）。Worker 偶爾會吃到舊版。 |

## 它能回答什麼

1. **這個車位停不停得進去？**
   單次進入所需的最短車位長度（靠牆 0.20m 時為 **6.27m**，約車長的 1.36 倍），
   拿來跟屋前空間的實際長度（**6.10m**）比較 —— 差 0.17m，所以非折不可。

2. **巷道哪裡最窄？**
   沿線掃描出最窄的斷面。現場配置在**車位後端**（x ≈ 4.1m，對面停車與車位後方停車
   對夾）只剩 **2.22m**，車寬 1.855m —— 左右合計 37cm。這種瓶頸常常比車位長度更致命，
   因為它讓「先開過車位再倒車」這個標準起手式根本做不到。

3. **要怎麼開？**
   Hybrid A* 搜出可行路徑，輸出成人看得懂的指令：
   「倒車 2.91m，回正」「倒車 0.75m，向牆側 1.35 圈（打到底）」。
   轉角只取「打到底／打一半／回正」這種人實際用的檔位。

4. **停不進去的話，要改什麼？**
   自動把每個障礙各挪一點、各移走一次、放寬靠牆距離、換方向停，重跑規劃，
   回報**最小的改動量**。例如現場配置的實測結果：

   > 把「對面機車群（右）」沿巷道往右挪 **0.3m** → 折 14 次變 **10 次**
   > 把「車位前方機車」沿巷道往右挪 **1.0m** → 折 14 次變 **6 次**

5. **出得來嗎？**
   駛出與停入共用同一條路徑（倒著走），所以兩者永遠一致。

## 挑戰

側欄最上面那一區。選一關，車回到起點、計數歸零，目標是把車停進車位。

關卡是**固定的題目** —— 同一條巷子的五種現場狀況，由鬆到緊：巷子寬一點、對面清空、
後車讓一公尺、現場原況、貼牆 8cm。每一關都從程式裡的預設場景長出來，不吃你自己調過的
設定，所以每次開始都是同一道題。

**計分：折返次數優先，同分才比總行程。** 跟規劃器判斷「哪種手法好開」用的是同一個順序。
每關的最佳成績存在這台裝置的瀏覽器裡。

開始挑戰時，車輛規格、巷道與車位、障礙物三個面板會鎖住，「從哪頭開進來」「入庫方式」
也一起停用 —— 改場景就是改題目，改了成績就沒得比。「放到定位」同樣鎖住，那是把車瞬移
進車位，等於一鍵過關。「回到起點」留著，它跟「重來」是同一件事。

**你自己的場景不會被挑戰洗掉。** 進入挑戰時會先把它收起來，存檔一律存那一份，
按「結束挑戰」就換回來。

**回放**：按「回放這次」，你剛才每一下按鍵會被併成路段、掛上原本的時間軸播放器，
可以拖著逐步看。勾「同時顯示規劃器的路徑」，規劃器的車與軌跡會用灰色一起播；
兩條路徑長度不同，是按**完成比例**對齊的，所以看得出誰在哪一段多繞了。

## 介面配置

標題下方有**兩個分頁**，地圖兩邊共用：

- **模擬** —— 駕駛列、時間軸、挑戰、可行性分析、顯示選項。
- **環境設置** —— 障礙物、巷道與車位、車輛規格。

分開的理由是距離：原本兩件事擠在同一個側欄，障礙物編輯器排在最下面，
拉一根滑桿要在畫面上下來回看。分頁之後該用的面板就與地圖齊高。
障礙物排在設置頁最上面，那是最常調的東西。挑戰進行中環境設置頁會停用 ——
改場景就是改題目。選了哪一頁會跟設定一起存起來。

手動駕駛的控制列在**圖的正下方**，不在側欄 —— 一邊開一邊看圖才有意義，
視線不用左右來回跳。

```
[◀ 打向牆側] [回正] [打向外側 ▶]  ── 方向盤滑桿 ──  向牆側 0.67 圈
[▼ 倒車 25cm] [▲ 前進 25cm]   車身角度／最近間隙／移動次數   [↶ 上一步] [回到起點] [放到定位]
```

方向盤按鈕一次打 1/4 個行程（連按四下到底），要微調用滑桿。

每次前進／倒車的距離可以選 **2 / 5 / 10 / 25 / 50 cm**，預設 10cm ——
車位只剩十幾公分餘裕時，25cm 一步就過頭了。選擇會跟著設定一起存起來。

鍵盤（按鍵標示直接印在按鈕上）：

| 鍵 | 動作 |
|---|---|
| `A` ／ `←` | 往畫面左邊開（距離可選） |
| `D` ／ `→` | 往畫面右邊開 |
| `Q` | 方向盤回正 |
| `空白鍵` | 播放／暫停已規劃的路徑 |
| 滑鼠滾輪 | 轉方向盤，往上打向外側，一格 2 度（游標在圖上或駕駛列上） |

按鍵對應的是**車子在圖上往哪邊移動**，不是前進倒車 —— 車頭朝右時按 `D` 是前進，
車頭朝左時按 `D` 就是倒車。俯視圖上車只沿巷道左右走，先把前進倒車在腦中換算成
左右再按鍵是多餘的一步。方向盤微調交給滾輪，所以 `W` `S` 與 `↑` `↓` 都收掉了。

游標在輸入欄或下拉選單裡時不會觸發（不然改障礙物名稱打到 a 車就跑掉了）。


圖的上方（住家建物那條帶子）原本是空的，現在放**參數列**：最常切換的三個方向設定
（從哪頭開進來／停妥車頭朝／入庫方式）＋三個關鍵讀數（可用車位／單次進入需求／
巷道最窄）。車位不夠長或巷子太窄時，該項讀數會轉紅。

圖例排在圖的下方而不是浮在圖上 —— 八列的直式圖例會蓋掉左半邊的路面。

## 場景怎麼設定

**直接在圖上拖曳**就能調整障礙物：

| 拖哪裡 | 效果 |
|---|---|
| 中間 | 沿巷道搬動 |
| 左右端 | 改長度（另一端釘住不動） |
| 面向巷道那一邊 | 改突出深度 |
| 機車群的左右端 | 增減台數（自動吸附到整數台） |
| 綠色車位框 | 換一個要停的空隙 |
| 牆上的大門／對面大門 | 沿巷道搬動；拖兩端改寬度 |
| 牆上的充電器 | 沿巷道搬動 |

機車群用**台數**而不是長度（現場數車比量長度直覺，一台以 0.55m 計）；
汽車與固定設施則是直接給長度。側邊的滑桿會同步更新，也可以反過來用滑桿微調。另外可以新增／刪除障礙、改類型
（汽車／機車群／固定設施）與所在側（住家側／對面側）。預設值依現場配置圖換算。

### 屋前空間長度

自家門面那一段的總長 —— 也就是住家側兩個障礙物之間的空隙，同時就是**可用車位**。
現場實測 **6.10m**（可停段 4.60 ＋ 大門 1.50）。

這個數字本來只是算出來的結果，但它是現場唯一拿捲尺量得到的東西，所以側欄給了一根
**屋前空間長度**滑桿可以直接輸入：拉它等於把「車位前方機車」搬遠或搬近，後端釘住不動。
反過來在圖上拖障礙物，滑桿也會跟著變 —— 兩個方向都通，不會有「輸入值」與
「算出來的值」對不起來的問題。

**大門不佔這個長度。** 它是牆上的參照物，不是障礙物：車照樣可以停在門前，
只是停完要檢查剩下的開口還走不走得過去（見下面「大門」那一節）。

可停段 4.60m 剛好等於車長，所以車只要跟鄰車留 0.15m，就正好從大門那頭吃掉 0.15m。

### 倒車入庫幾乎都比較好

平行停車的轉向輪在前，倒車時後軸當支點畫小圓進車位；前進入庫則是車尾甩不動，
得繞一大圈。把對面障礙清空做對照實驗（隔離變因）：

| 車位長 | 倒車入庫 | 前進入庫 |
|---|---|---|
| 5.90m | 折4 **8.1m** | 折4 **14.1m** |
| 6.50m | 折2 **7.9m** | 折2 **14.4m** |
| 8.00m | 折2 **8.6m** | 折2 **13.6m** |

**折返次數差不多，總行程卻差 40%。** 只看折返次數會完全錯過這件事，
所以介面上兩個數字都要看。

「自動」不是隨便挑一個，而是把兩種各搜一次再比分數（總行程 ＋ 折返 × 0.8），
並把比較結果列出來。以現場配置（屋前空間 6.10m）實測：自動挑了前進入庫
**折 14 · 26.6m**，指定倒車入庫是**折 20 · 28.4m** —— 這一次前進入庫真的比較好。

**所以通則不能拿來當結論。** 上面那張對照表說倒車入庫幾乎都贏，但那是把對面清空、
只留車位長度這一個變因；現場的巷道瓶頸會把倒車的優勢吃掉。兩種都搜過再比，
才不會拿通則去猜。

還可以指定**入庫方式**：自動／倒車入庫／前進入庫。選了之後畫面上的起點會跟著換：

- **前進入庫**：車頭停在車位邊緣前 0.5m，還沒開到車位
- **倒車入庫**：已經開過車位、**車尾與車位前緣切齊**，也就是「與前車並排」

起手位置放錯會讓答案失真。原本倒車入庫的起點是跨在空車位上（等於偷跑），
改成正確的並排位置後折返次數才誠實 —— 現場配置實測是折 20 次。

**停妥車頭朝向不能選，是推導出來的。** 入庫方式不影響車頭朝向 —— 那是垂直車格
才有的事（倒車入庫車頭朝外、前進入庫車頭朝內，差 180°）。平行停車不管倒車或前進，
車最後都與牆平行、車頭沿著進來的方向：

> 從左邊進來 ＝ 往右開 ＝ 車頭朝右（兩者相反）

要停成反方向就得在巷內調頭，這條巷子做不到，所以介面不提供這個選項，
免得選到必然無解的組合。介面上「停妥車頭朝」是唯讀顯示，跟著「從哪頭開進來」變。

因為停入與駛出是同一條路徑倒著走，倒車入庫 ⇔ 前進駛出。以現場配置實測，車位越緊倒車入庫越划算：
屋前空間縮到 5.35m 時，倒車入庫折 12 次 · 18.6m，前進入庫要折 20 次 · 26.5m ——
跟 6.10m 時的結論剛好相反。

車頭在圖上有明確標示（藍色車頭區塊、白色箭頭、「車頭」二字），
目標車位框上也有箭頭標出停妥後車頭朝哪。

## 停哪裡：貼緊鄰車，不是停在正中間

實際使用上有個硬條件：**車要貼緊旁邊那台車，另一頭才留得出開門的空間**。
所以目標位置不是車位正中間，而是由「與鄰車間距」決定（預設 0.15m）。

要貼的是**汽車**，而且**與停車方向無關**。一開始寫成「依車頭方向貼前面那一端」，
結果車頭朝右時就去貼機車了 —— 那沒有意義：汽車是固定又平整的參考物，
機車歪歪斜斜還會被挪走。程式會找出車位兩端哪一端是 `kind: 'car'` 的障礙，
往那一端靠。

這個約束**不是**為了比較好停 —— 現場配置實測，貼緊鄰車（0.15m）倒車入庫折 20 次 · 28.4m，
停在正中間（0.75m）也是折 20 次，總行程還短一點（24.7m）。餘裕集中在同一端對搓車有幫助，
但在這個場地不明顯。貼緊鄰車真正的理由是下面那一節：**把大門讓出來**。

實測 0.05m～1.00m 掃描，倒車／前進入庫共 40 組全部有解，實際停出來的間距
與設定值相差多在 5cm 內。

## 大門：真正決定停車位置的東西

住家牆上有大門。它不是障礙物（車不會撞到牆上的開口），所以不進碰撞檢查 ——
但擋住了人就出不來，對使用者來說跟停不進去一樣糟。

以現場尺寸來說大門**必然會被擋掉一部分**（車位起點就在大門旁邊），所以重點
不是「有沒有擋到」，而是**剩下的連續開口還走不走得過去**（以 0.55m 為門檻）：

| 與鄰車間距 | 大門可通行 | |
|---|---|---|
| **0.15m** | **1.35m** | 只被車頭切掉 0.15m |
| 0.60m | 0.90m | 還過得去 |
| 1.20m | 0.30m | 過不去 |

（以實測的門面配置計算：鄰車 0.38～4.43、可停段到 9.03、大門 9.03～10.53、車 4.58～9.18。
可停段 4.60m 剛好等於車長，所以跟鄰車留多少，就從大門那頭吃掉多少。）

**這就是「必須貼緊鄰車」的真正原因。** 圖上大門被擋住的那一段畫紅色，
剩下的開口畫綠色並標出寬度；參數列也有「大門可通行」讀數，低於門檻轉紅。

對面建物也有大門，同樣標出來。它擋不到你停車，但**門前只停得下一台機車** ——
排不了一整排。這件事直接改變巷道最窄處落在哪裡：改成一台之後，車位正前方那段全淨空，
最窄處移到**車位後端**（對面停車與車位後方停車對夾，**2.22m**）。

充電線在目前的充電器位置（x = 8.10m）下不構成取捨：貼緊鄰車 **0.95m**、
停在正中間 **0.38m**，兩個都夠短。充電器要是裝在門面的另一頭，才會變成
「讓出大門」與「拉長充電線」二選一 —— 模擬器把兩個數字都擺著，換個位置就自己看得到。

## 充電

住家牆上的充電器與車上的充電口都畫進場景，並算出**充電線要拉多遠**。

車上充電口的位置是「駕駛座前面一點」——台灣右駕道路、駕駛座在左，所以在**車身左側**。
車頭朝右時左側才會朝住家牆，而且車頭正好朝向充電器那一端，所以**朝右才是充電方向**。
以預設值實測：

| 停妥車頭朝 | 充電線長度 |
|---|---|
| **右** | **0.95 m** |
| 左 | 2.56 m |

充電器可以直接在圖上拖（判定範圍比圖示大一圈，圖示本身只有 0.38m 寬、
螢幕上約 12px，照原尺寸判定會很難點），充電口距車頭的距離用滑桿調，圖上即時畫出充電線與長度。
超過 5m 會轉紅。

## 左右怎麼算

圖上所有的**左右都是看圖的左右**：圖左＝巷子左，對應底部的公尺刻度。
「把機車往右挪 0.3m」指的是往刻度變大的方向。

車角讀數則刻意**不用左右**，改成「牆側前角／牆側後角／外側前角／外側後角」——
因為車頭朝左或朝右時，同一個角的左右會翻轉，而看圖的人和坐在車上的人講的
又是不同的左右。用「靠牆／靠外」就沒有這個問題，而且那本來就是開車時在意的方向。

## 設定會自動保存

場景是一格一格量出來、拖出來的，重新整理就沒了很難用。所有設定
（巷道尺寸、每個障礙物、大門、充電器、顯示選項）都會存進 `localStorage`，
key 是 `rav4-parking-sim/v1`。

讀回來時與預設值合併，之後程式新增欄位不會讓舊資料壞掉；讀取與寫入都包在
try/catch 裡（無痕視窗或封鎖網站資料時會丟例外），失敗就當作沒存過。
「全部重設」把所有設定改回預設值。

介面上有一行**狀態**會說明實際發生什麼事：「已還原 ⟨時間⟩ 的設定」／
「這台裝置還沒存過設定」／「瀏覽器不允許儲存」／「存檔讀不出來」。
設定沒還原時先看這一行，不用猜。

寫入有 300ms 防抖，另外在 `pagehide` 與分頁隱藏時補寫一次 ——
不然改完馬上按重新整理，最後一次修改會來不及存。

## 幾個刻意的決定

**車輛規格可調，而且填的是規格表上查得到的數字。** 介面上給的是車長／車寬／
軸距／**最小迴轉半徑**，最大轉向角由迴轉半徑反推：

```
R_外前輪 = hypot(R_後軸 + 輪距/2, 軸距)
→ R_後軸 = sqrt(R_外前輪² - 軸距²) - 輪距/2
→ δmax  = atan(軸距 / R_後軸)
```

要人猜「前輪最大轉幾度」不切實際，但迴轉半徑規格表上就有。

預設是 RAV4 PHEV（XA50）：長 4.60m、寬 1.855m、軸距 2.69m、迴轉半徑 5.70m
→ 後軸半徑 4.23m、δmax 32.5°。**PHEV 標配 19 吋輪是 5.70m，一般版 17 吋才是
5.50m** —— 差 0.2m 看似不多，換算成後軸半徑是 4.23 vs 3.99m，在只差十幾公分的
車位裡差很多。參考版寫死 38°，比實車樂觀太多。

改車長或軸距時前後懸會依原廠比例自動重算（長 = 前懸 + 軸距 + 後懸）。

**狀態點取後軸中心。** 後軸才是實車的瞬時迴轉基準。用車體中心積分（參考版的做法）
會讓迴轉半徑與軌跡都失真。

**一律從車位往外搜，停入是把結果倒著走。** 自行車模型時間可逆，反轉的路徑一樣合法，
但方向差很多：從車道往死角搜，啟發式一路指向口袋深處，要在極窄空間裡碰運氣；
從車位往外搜則是往越來越開闊的地方展開。改方向後，現場配置從「12 秒後宣告無解」
變成「86ms 找到解」，而且再也不會出現「出得來卻進不去」這種不可能的結論。

**停妥是一個區域，不是一個點。** 原本把目標寫死成「車位正中間、離牆剛好 wallGap」。
實際開車本來就是能停哪就停哪；寫死成一個點會製造假的無解。

**取樣間距跟安全裕度掛鉤。** 固定 8cm 取樣時，滿舵每步車身轉 0.02 rad，
最遠的車角位移 5cm —— 比 2cm 的裕度還大，車角會從兩個取樣點之間掃過障礙。
讓車角單步位移不超過裕度就不會發生。

**位置偏好用代價，不用硬約束。** 「要貼緊前車」如果寫成硬性的位置限制，
在只剩幾十公分餘裕的車位裡，能不能停就變成取決於格線剛好切在哪裡 ——
會出現「間距 0.10 和 0.30 有解、0.15 卻無解」這種假無解。改成給每個候選停車位置
一個「離理想位置多遠」的起始代價，搜尋自然會偏好貼緊的解，又不會憑空判死。

**假無解要濾掉。** 同理，起點不在格子上先去重，而且最後多跑一層換過格距的搜尋。
只差 5cm 的設定一個有解一個無解，那是離散化的運氣，不是幾何。

**搓車需要很細的角度格子。** 車位前後被深障礙夾住時，唯一出路是反覆小幅前後搓、
每次多轉 2 度多。角度去重格距若是 6°，搓兩下還落在同一格就被剪掉，
於是搜尋提早宣告無解。專門的 shuffle 層用 2° 格距並調低換檔代價。

**碰撞用特化版 SAT。** 障礙都是軸對齊矩形，用 OBB(車) vs AABB(障礙) 的四軸測試，
每個障礙約 20 次浮點運算，讓搜尋達到每秒數萬節點。

## 換車比較

車輛規格可調的用處：可以直接跑「換一台車會不會比較好停」。以現場配置實測：

| 車 | 尺寸 | 迴轉半徑 | 理想最短車位 | 規劃結果 |
|---|---|---|---|---|
| RAV4 PHEV | 4.60 × 1.855 | 5.70m | 6.27m | 前入 折14 · 26.6m |
| 舊車 | 4.78 × 1.78 | 5.40m | 6.31m | 倒入 **折14 · 21.5m** |

舊車**比較長**（連理想最短車位都多 4cm）卻比較好停：折返次數一樣，總行程少了
5.1m（**19%**），而且它是用倒車入庫做到的。窄了 7.5cm、迴轉半徑小 0.3m，
這兩點加起來蓋過了車長的劣勢。這與實際經驗一致，也是這個模型的一個對照驗證。

## 已知限制

- 障礙物都是靜態矩形，不會動；機車群當成一個整塊處理。
- 只模擬平面運動，不含坡度、路面摩擦、轉向速率上限（實車不可能瞬間打死方向盤）。
- 現場尺寸靠滑桿輸入，預設值是從配置圖換算的估計值。量過再填才準 ——
  尤其是車位前後障礙的**突出深度**，它對答案的影響比想像中大：
  同樣 5.8m 車位，鄰車深 1.2m 只要折 2 次，深 1.9m 要折 16 次。
- 「折 34 次」這種解幾何上成立，實務上等於停不進去。介面在折返超過 8 次時會直說。
